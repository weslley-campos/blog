# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Kotlin Multiplatform + Compose Multiplatform blog app targeting **Android**, **JVM/Desktop**, and **Wasm/JS** (browser). The Wasm/JS target is the primary deployment (served via nginx in `Dockerfile`); Android and JVM exist mostly to enable Compose previews and rapid iteration.

Root package for everything is `br.com.weslleycampos.blog` (defined as `Project.blogPackage` in `build-logic`).

## Common commands

Use the Gradle wrapper (`./gradlew`). JDK 17 is required — `settings.gradle.kts` enforces this.

| Task | Command |
|---|---|
| Run web app (dev server on `:5001`) | `./gradlew :composeApp:wasmJsBrowserDevelopmentRun` |
| Build web production bundle | `./gradlew :composeApp:wasmJsBrowserDistribution` |
| Run desktop app | `./gradlew :composeApp:run` |
| Hot-reload desktop dev | `./gradlew :composeApp:runHot` (compose-hot-reload plugin is applied to `composeApp`) |
| Run all JVM tests | `./gradlew jvmTest` |
| Run a single test class | `./gradlew :core:markdown:jvmTest --tests "br.com.weslleycampos.blog.core.markdown.processing.MarkdownParserTest"` |
| Run Detekt (lint + auto-correct) | `./gradlew detekt` |
| Build everything | `./gradlew build` |

Notes:
- `testDebugUnitTest` / `testReleaseUnitTest` (Android) are **disabled** in `build-logic/.../Android.kt` — Android target exists only to enable Compose previews and KSP. Don't try to run Android unit tests; use `jvmTest`.
- `wasmJs` `testTask` is also disabled in convention plugins.
- CI (`.github/workflows/deploy.yml`) runs `./gradlew detekt` then `./gradlew jvmTest`, then on `main` SSHes to a server to rebuild and restart the Docker container.

## Architecture

### Module graph

```
composeApp (KMP application — Android/JVM/Wasm entry points)
├── core/ui            ← BlogTheme, design system tokens, shared composables
├── core/common        ← PreferencesManager (DataStore), BlogKoinApp, Flow extensions
├── core/navigation    ← Navigator, EntryProvider, NavKey definitions for every feature
├── core/markdown      ← Standalone Markdown parser + Compose renderer (see core/markdown/README.md)
├── feature/home       ← Home screen + nav wiring
└── feature/about      ← About screen + nav wiring
```

`feature/favorites/` exists on disk (with build output) but is **not** included in `settings.gradle.kts` — treat it as not part of the project unless explicitly re-added.

### Build conventions (`build-logic/`)

`build-logic/` is an included build that publishes six convention plugins. Modules apply them via the version catalog (`libs.plugins.blog.*`):

| Plugin alias | What it does |
|---|---|
| `blog.application` | Applies KMP + Android application + serialization; configures all targets (jvm, androidTarget, wasmJs) |
| `blog.library` | Same but for libraries (`androidLibrary`, `wasmJs.binaries.library()`) |
| `blog.compose.application` / `blog.compose.library` | Adds Compose Multiplatform plugin and the full Compose dependency stack (Material3, navigation3, lifecycle, adaptive) — see `build-logic/.../extensions/Compose.kt` for the curated list |
| `blog.koin` | Adds Koin BOM, koin-core, koin-annotations, KSP. Wires `kspCommonMainKotlinMetadata` as a dependency of every other `ksp*` task (works around a known KMP+KSP ordering bug). |
| `blog.detekt` | Adds Detekt with shared `detekt.yml`, includes formatting plugin, `autoCorrect = true` |

Compiler flags applied to all Kotlin source sets: `-Xexpect-actual-classes`, `-Xexplicit-backing-fields`, `-Xenable-suspend-function-exporting`, `-Xdata-flow-based-exhaustiveness`. Type-safe project accessors are enabled — use `projects.feature.home`, not `project(":feature:home")`.

When editing convention plugins, the build-logic module itself targets JDK 17 (`build-logic/convention/build.gradle.kts`).

### Dependency injection (Koin annotations + KSP)

DI is **annotation-based** Koin, generated by KSP. There is no manual module DSL.

- Each module exposes a class annotated `@Module @ComponentScan` (e.g., `HomeModule`, `NavigationModule`, `CommonModule`). `composeApp/AppModule.kt` aggregates them via `includes = [...]`.
- Components are declared with `@Single`, `@Factory`, `@KoinViewModel`. Constructor params injected from a runtime context use `@Provided`.
- The Koin app is bootstrapped from `BlogKoinApp` (annotated `@KoinApplication`). Both `wasmJsMain/main.kt` and `jvmMain/main.kt` call `BlogKoinApp.startKoin { modules(AppModule().module) }` — `AppModule().module` is a generated extension produced by KSP under `org.koin.ksp.generated`.
- KSP options set globally: `KOIN_CONFIG_CHECK=true`, `KOIN_LOG_TIMES=true`.
- After adding a `@Single`/`@Module` annotation, run a Gradle build (or at minimum `kspCommonMainKotlinMetadata`) so the generated code is available.

**When adding a new module that uses Koin**: it must have a `@Module @ComponentScan` class at the package root, and that class must be added to `AppModule`'s `includes` array — otherwise its components won't be discovered.

### Navigation (Jetpack Navigation 3, multiplatform)

The app uses `androidx.navigation3` (multiplatform port). Navigation is decentralized: each feature module owns its own entry, but the `NavKey` lives in `core/navigation/entries/<feature>/`.

The plumbing — see existing wiring in `feature/home` for the canonical example:

1. **`<Name>Entry`** — a `@Serializable object : NavKey` in `core/navigation/entries/<name>/`. This is the route identifier.
2. **`<name>EntryBuilder()`** — extension on `EntryProviderScope<NavKey>` that calls `entry<NameEntry> { NameScreen() }`. Lives in the feature module under `navigation/`.
3. **`<Name>EntryProvider`** — `@Single(binds = [EntryProvider::class])` class implementing `EntryProvider` with a `serializerModule()` (registers polymorphic `NavKey` subclass) and `entryBuilder()` (returns the lambda from step 2).
4. **`EntriesAggregator`** — Koin injects `List<EntryProvider>` (collected from every `@Single(binds = [EntryProvider::class])`). The `main()` functions iterate this list to build the polymorphic `SerializersModule` and the combined entry provider passed to `NavDisplay`.
5. **`Navigator`** — singleton wrapping `NavBackStack<NavKey>`; injected with the start entry as a `@Provided` param (`HomeEntry` is passed via `parametersOf` in `main`).

So adding a new screen is: define `NavKey` in `core/navigation`, add `EntryBuilder` + `EntryProvider` in the feature module, and the aggregator picks it up automatically. **Don't manually edit a navigation graph** — there isn't one.

There is a skill at `.claude/skills/module-creator/SKILL.md` with a full step-by-step recipe for scaffolding new modules (core / feature / domain). Prefer following that recipe when adding a module so naming, package paths, and gitignore stay consistent.

### Theming, preferences, i18n

- Theme & language are driven by `AppViewModel` in `composeApp/`, which observes `PreferencesManager` flows (DataStore-backed, shared via `core/common`). `PreferencesDataStoreProvider` has per-platform `actual` implementations (Android, JVM, wasmJs).
- `BlogTheme` (`core/ui/theme/Theme.kt`) provides `BlogTheme.colors`, typography, spacing, shapes, sizes, gradients, icons via composition locals — features should pull tokens from `BlogTheme` rather than `MaterialTheme` directly.
- `BlogTopBar` exposes `onThemeToggle` and `onSelectLanguage` which write back to preferences via the view model.

### Markdown module

`core/markdown` is a self-contained sub-library with its own README (`core/markdown/README.md`). It uses a **processor chain** pattern: the parser tries each `Processor` in order; the first non-null result wins. Adding a block type means adding a new `@Single` class implementing `Processor`. Models are sealed classes (`MarkdownBlock`, `InlineMarkdown`) — Kotlin's exhaustive `when` is the safety net. The parser returns `ImmutableList<MarkdownBlock>` (kotlinx-collections-immutable) for Compose-friendly state.

## Conventions worth knowing

- **Package layout** for every module: `src/commonMain/kotlin/br/com/weslleycampos/blog/<category>/<module-name>/...` (matches the rule in `build-logic/.../extensions/Project.kt` `packageName`/`resourcePackage`).
- **Compose resources** use a generated class named after the module path (e.g., `FeatureHomeRes`, `CoreUiRes`) — see `toResClassName()` in `Project.kt`. Package is `<module-package>.resources`.
- **Detekt** has `autoCorrect = true` and excludes `**/build/**`. `FunctionNaming` ignores `@Composable` and `@Test`. `MagicNumber` ignores property/local declarations.
- The `composeApp/wasmJsMain/main.kt` filename is exempted from Detekt's `Filename` rule (it has `fun main()` not matching the file name).
- Commit messages in this repo follow an emoji + conventional-commit style (e.g., `⚙️ chore:`, `♻️ refactor:`, `✨ feat:`). The `.claude/skills/commit-message/` skill enforces this — invoke it via `/commit-message` rather than hand-rolling.
